### Fluxo principal do MVP (é o que precisa estar publicado)
Visitante abre a URL → busca por especialidade → abre a página do profissional → vê horários
livres → cadastra-se / faz login → marca a consulta → vê a confirmação em "Minhas consultas".

### Critérios adiados (não implementar hoje; nenhuma spec é alterada)
Por depender de partes fora do MVP ou por prazo. Estes itens **não** contam como "pronto" e
ficam listados no fim do `TASKS`:

- **Cadastro e login:** recuperação de senha, convite de profissional/recepção, edição de perfil,
  exclusão/anonimização de conta, tela "esqueci/redefinir senha", tela "meu perfil".
- **Clínicas e profissionais:** nota média na página pública (depende de Avaliações — mostra
  "sem avaliações"); upload de foto (só campo `foto_url`).
- **Agenda:** visão em calendário (no MVP a agenda do profissional é uma lista por dia/semana
  colorida por status).
- **Busca:** filtro por convênio (depende de Convênios); ordenação por nota média (depende de
  Avaliações).
- **Agendamento:** pagamento por convênio (só `particular`); lista de espera.
- **Publicação:** nada adiado.

Consequência sobre a regra de autenticação da visão geral: profissionais criados pelo admin no
MVP não têm login (sem convite); os usuários com login de profissional/recepção/admin vêm do
`seed`.

## 2. Arquitetura

```
Navegador ── React (build Vite, servido como estático) ──┐
                                                         │  mesmo domínio
                         FastAPI ── /api/*  ─────────────┘
                            │
                     SQLAlchemy 2 (sync, psycopg 3)
                            │
                   PostgreSQL (Render) + Alembic
```

- **Um único serviço** (Dockerfile na raiz, multi-stage): estágio Node gera `dist/`; estágio
  Python copia `dist/` para `app/static/` e o FastAPI serve `/api/*` + arquivos estáticos, com
  fallback para `index.html` em qualquer rota não-API (SPA).
- Início do container: `alembic upgrade head && python -m app.seed --se-vazio && uvicorn ...`.
  O seed é idempotente (não roda se já existir o admin de demonstração), porque o plano gratuito
  do Render não tem shell.
- **Testes do backend em PostgreSQL**: `TEST_DATABASE_URL` (serviço `postgres` no GitHub Actions)
  ou, sem essa variável, um PostgreSQL embutido via `pgserver` (dependência só de
  desenvolvimento; a máquina de desenvolvimento não tem Docker). Motivo: o lock de linha
  (`SELECT ... FOR UPDATE`) e o índice único parcial da marcação precisam de PostgreSQL de verdade.

### Backend — `src/backend/`
```
app/
  main.py               # cria app, inclui routers, monta estáticos + fallback SPA
  core/config.py        # Settings (pydantic-settings) lendo env: DATABASE_URL, JWT_SECRET, ...
  core/db.py            # engine, SessionLocal, Base, get_db
  core/seguranca.py     # hash bcrypt, JWT, dependência usuario_atual, exige_perfil(...)
  core/tempo.py         # agora_utc(), conversões UTC <-> America/Sao_Paulo
  core/texto.py         # normalizar(): sem acento + minúsculas (busca)
  core/erros.py         # exceções de domínio -> HTTP (409, 422, 403) com mensagem em pt-BR
  health/router.py
  auth/{models,schemas,service,router}.py
  clinicas/{models,schemas,service,router}.py
  agenda/{models,schemas,service,router}.py
  busca/{schemas,service,router}.py
  agendamento/{models,schemas,service,router}.py
  seed.py
alembic/ + alembic.ini
requirements.txt
```
Libs: fastapi, uvicorn[standard], sqlalchemy>=2, alembic, psycopg[binary], pydantic-settings,
pyjwt, bcrypt, email-validator; testes: pytest, httpx.

Regras de camada: `router` só valida entrada/saída e chama `service`; regras de negócio ficam
em `service` (é onde os testes de regra batem, além dos testes de API).

de `/api` para `localhost:8000`.

### Convenções transversais
- Datas: colunas `timestamptz` em UTC; a grade semanal guarda `time` **local**
  (`America/Sao_Paulo`) e é convertida para UTC ao calcular horários. Frontend exibe com
  `Intl.DateTimeFormat('pt-BR', { timeZone: 'America/Sao_Paulo' })`.
- Dinheiro: `preco_centavos` inteiro; formatação só no frontend.
- Erros: corpo `{"detail": "<mensagem em português>", ...}`; 409 de conflito traz a lista de
  consultas afetadas em `"consultas"`.
- Autorização: tudo exige token, exceto `POST /api/auth/cadastro`, `POST /api/auth/login`,
  `POST /api/auth/renovar`, `GET /api/health` e `GET /api/publico/*` (busca pública).

## 3. Modelos de dados

Todas as tabelas têm `id` inteiro (PK). `criado_em timestamptz default now()` onde fizer sentido.

### auth
**usuarios** — `nome`, `email` (único, minúsculas), `cpf` (único, só dígitos, nulo para
não-pacientes), `data_nascimento` (date, nulo), `telefone`, `senha_hash`,
`perfil` (enum `paciente|profissional|recepcao|admin`), `ativo` (bool),
`tentativas_falhas` (int, default 0), `bloqueado_ate` (timestamptz, nulo).

**tokens_renovacao** — `usuario_id` FK, `token_hash` (sha256, único), `expira_em`,
`revogado_em` (nulo). Logout preenche `revogado_em`.

### clinicas
**unidades** — `nome`, `endereco`, `cep` (8 dígitos), `telefone`, `abertura` (time),
`fechamento` (time), `dias_funcionamento` (int[] 0=seg … 6=dom), `ativa` (bool).

**especialidades** — `nome` (único), `nome_busca` (normalizado, índice).

**tipos_consulta** — `especialidade_id` FK, `nome`, `duracao_min`
(CHECK 15–120 e múltiplo de 5), `preco_centavos` (int ≥ 0).

**profissionais** — `usuario_id` FK nulo, `nome`, `nome_busca`, `conselho` (ex.: CRM),
`registro_numero`, `registro_uf` (2 letras), UNIQUE(`conselho`,`registro_numero`,`registro_uf`),
`foto_url` (nulo), `biografia` (≤ 500), `ativo`.

**profissional_especialidade** (`profissional_id`, `especialidade_id`) e
**profissional_unidade** (`profissional_id`, `unidade_id`) — tabelas de associação.

### agenda
**grade_horarios** — `profissional_id`, `unidade_id`, `dia_semana` (0–6), `hora_inicio`,
`hora_fim` (time local; CHECK início < fim). Sobreposição do mesmo profissional (qualquer
unidade) e limite do horário da unidade são validados no `service`.

**bloqueios** — `profissional_id`, `inicio`, `fim` (timestamptz), `motivo`.

**feriados** — `data` (date), `nome`, `unidade_id` (nulo = nacional).
UNIQUE(`data`, `unidade_id`).

### agendamento
**consultas** — `paciente_id` FK usuarios, `profissional_id`, `unidade_id`, `tipo_consulta_id`,
`inicio`, `fim` (timestamptz), `status` (enum `marcada|confirmada|em_atendimento|realizada|
cancelada_paciente|cancelada_clinica|faltou`), `forma_pagamento` (`particular` no MVP),
`preco_centavos`, `remarcacoes` (int, ≤ 2), `consulta_origem_id` (FK nulo, para remarcação),
`criado_por_id` FK usuarios.
**Garantia anti-duplicidade (banco)** — revisado em 06/10: o PostgreSQL embutido usado nos
testes locais não tem `btree_gist`, então em vez de `EXCLUDE` usamos **lock + índice único**:
a marcação faz `SELECT ... FROM profissionais WHERE id = :id FOR UPDATE` (serializa pedidos do
mesmo profissional), confere sobreposição dentro da transação e insere; além disso há
`UNIQUE INDEX (profissional_id, inicio) WHERE status IN ('marcada','confirmada','em_atendimento')`.
Qualquer conflito vira 409 "horário não está mais disponível".

**historico_status** — `consulta_id`, `de_status` (nulo na criação), `para_status`,
`usuario_id`, `em`.

### Regras calculadas (no `service`, com teste cada uma)
- **Horários livres** (`agenda.service.horarios_livres(prof, tipo, de, ate)`): para cada dia do
  intervalo (≤ 31 dias) que não é feriado nacional/da unidade, para cada faixa da grade
  daquele dia da semana, gerar inícios em passos de `duracao_min` cabendo inteiros na faixa;
  descartar os que colidem com bloqueio ou consulta ativa e os com início < agora + 2h.
- **Transições de status**: tabela em `agendamento.service.TRANSICOES`; inválida → 422.
- **Marcar**: horário precisa estar entre os livres; paciente sem sobreposição; ≤ 3 futuras
  `marcada`; paciente com 3 `faltou` em 90 dias bloqueado na web por 30 dias (recepção pode).
- **Cancelar** pelo paciente só até 24h antes; recepção a qualquer momento (`cancelada_clinica`).
- **Remarcar** numa transação: cancela a original e cria a nova (`remarcacoes + 1`,
  `consulta_origem_id`); falhou a nova → rollback, original intacta. Máx. 2.
- **Busca / próximo horário livre**: carrega em lote (uma consulta por tabela) grade, bloqueios,
  feriados e consultas dos profissionais filtrados para os próximos 31 dias e calcula em memória,
  parando no primeiro horário livre de cada um. Tipo de consulta usado: o de menor duração da
  especialidade filtrada (ou de qualquer especialidade do profissional). Preço exibido: menor
  `preco_centavos` desses tipos. Turnos (horário local): manhã 06–12, tarde 12–18, noite 18–24.

## 4. Rotas da API (prefixo `/api`)

### Saúde e público (sem login)
| Método | Rota | Descrição |
|---|---|---|
| GET | `/health` | `{"status":"ok","versao":"<hash>"}` (env `RENDER_GIT_COMMIT`/`GIT_COMMIT`) |
| GET | `/publico/filtros` | especialidades e unidades ativas (para os selects) |
| GET | `/publico/profissionais` | busca: `especialidade_id, unidade_id, nome, data, turno, ordem=(proximo\|preco), pagina` → 10/página |
| GET | `/publico/profissionais/{id}` | página pública: nome, foto, bio, especialidades (com tipos/preços), unidades |
| GET | `/publico/profissionais/{id}/horarios-livres` | `tipo_consulta_id, de, ate` (≤ 31 dias) |

### Autenticação
| Método | Rota | Perfil | Descrição |
|---|---|---|---|
| POST | `/auth/cadastro` | — | cadastro de paciente → 201 |
| POST | `/auth/login` | — | `{access_token, refresh_token}`; 401 credencial; 423 conta bloqueada |
| POST | `/auth/renovar` | — | novo access token a partir do refresh |
| POST | `/auth/logout` | logado | revoga o refresh token |
| GET | `/auth/eu` | logado | dados do usuário e perfil |

### Clínicas e profissionais (admin; leitura de unidades/especialidades também para recepção/profissional)

|---|---|---|
| GET/POST | `/unidades` | lista paginada (20, `q`, `ordem`) / cria |
| PATCH | `/unidades/{id}` | edita |
| POST | `/unidades/{id}/desativar` | 409 + lista se houver consultas futuras |
| GET/POST | `/especialidades` | lista paginada / cria (nome único → 409) |
| PATCH | `/especialidades/{id}` | edita |
| POST | `/especialidades/{id}/tipos-consulta` | cria tipo (duração 15–120, múltiplo de 5) |

| GET/POST | `/profissionais` | lista paginada (20, `q`, `ordem`) / cria |
| GET/PATCH | `/profissionais/{id}` | detalhe / edita (especialidades, unidades) |
| POST | `/profissionais/{id}/desativar` | 409 + lista se houver consultas futuras |

### Agenda (profissional dono ou admin; leitura de agenda também recepção)
| Método | Rota | Descrição |
|---|---|---|
| GET/POST | `/profissionais/{id}/grade` | lista / cria faixa (sobreposição ou fora do funcionamento → 422) |
| DELETE | `/grade/{id}` | remove faixa |
| GET/POST | `/profissionais/{id}/bloqueios` | lista / cria (colisão → 409 com consultas) |
| DELETE | `/bloqueios/{id}` | remove |
| GET/POST | `/feriados` | admin: lista / cria |
| DELETE | `/feriados/{id}` | admin |
| GET | `/profissionais/{id}/agenda` | `de, ate` → consultas com status (dia/semana) |
| GET | `/eu/profissional` | atalho: profissional do usuário logado |

### Agendamento
| Método | Rota | Perfil | Descrição |
|---|---|---|---|
| POST | `/consultas` | paciente, recepcao | marca (`paciente_id` obrigatório se recepção) → 201; 409 horário; 422 regras |
| GET | `/consultas/minhas` | paciente | `{proximas: [...], passadas: [...]}` com `pode_cancelar`, `pode_remarcar` |
| GET | `/consultas/{id}` | dono, recepcao, admin, profissional da consulta | detalhe |
| POST | `/consultas/{id}/cancelar` | paciente (≤ 24h antes), recepcao | |
| POST | `/consultas/{id}/remarcar` | paciente, recepcao | `{inicio}` (mesmo profissional/tipo/unidade) |
| GET | `/consultas/{id}/historico` | idem detalhe | histórico de status |
| GET | `/pacientes` | recepcao, admin | `q` por nome/CPF/e-mail (para marcar em nome) |

## 7. Testes

- Cada critério de aceitação **incluído no MVP** vira ≥ 1 teste (nome do teste cita o critério).
- Backend (`tests/backend/`): `conftest.py` cria o schema no banco de teste, transação por
  teste com rollback, `TestClient`, fábricas simples de dados, e relógio controlável
  (`core.tempo.agora_utc` substituível) para regras de 2h/24h/90 dias.
- Concorrência: duas threads com sessões próprias marcando o mesmo horário → exatamente um 201 e
  um 409.
- Desempenho da busca: 200 profissionais gerados → resposta < 1 s.
- Frontend (`tests/frontend/`): telas de cadastro/login (validação e erro em português),
  resultados de busca (render + filtros na URL), seletor de horários, Minhas consultas
  (botões conforme `pode_cancelar`). `fetch` mockado.

## 8. Riscos e cortes de emergência

- Se o horário apertar, cortar nesta ordem: telas admin (o seed cobre os dados) → tela da
  recepção → visão semanal da agenda. **Nunca** cortar o deploy nem o teste de concorrência.
- Docker no Windows indisponível → usar PostgreSQL local instalado ou o banco do Render
  (outro database) só para testes.
- Cold start do Render (até 1 min) — avisado no README.
